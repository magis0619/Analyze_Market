# DELVERS（仮題）— Claude Code 向け実装指示書 v2

## 0. 最初に読むこと

**これは OUTFITTER の仕様変更ではなく、ジャンルの変更である。**
OUTFITTER で実装済みの資産のうち、流用するものと破棄するものを §1 に明記した。
**§1 を実行してから §2 以降に着手すること。**

### 判定の原則（全工程に適用）

1. **「AAA品質」「良い感じ」「洗練された」といった抽象語で品質を判定してはならない。**
   判定は常に、§10 で各担当に割り当てられた**実在するベンチマーク作品との比較**で行う。
2. **実装したエージェントに自己採点をさせない。** 品質判定は必ず別のエージェントが行う（§11）。
3. **完成の宣言は、未達リストの提出とセットでのみ認める。**「完璧です」という報告は、
   未達リストが添えられていない限り無効として差し戻す。
4. 仕様に書かれていない機能を親切心で追加しないこと。迷ったら §12 のスコープ表に従う。

## 2. ゲームの定義

> **プレイヤーは出撃前に3つの判断をするだけ。あとはアプリを閉じる。
> 帰ってきた10個の未鑑定品を開ける瞬間が、このゲームの全てである。**

- プレイヤーは戦闘を一切見ない。操作もしない
- 判断は「装備」「撤退ルール」「派遣先」の3つのみ
- 1日2〜3回、各3分の起動を想定する

## 4. ゲームループ

### 4.1 全体構造

```
【拠点】プレイヤーが操作する唯一の場所
 ├ 帰還レポート確認
 ├ 未鑑定品を一括開封（稀少以上はカットイン）
 ├ インベントリ整理（ソート／フィルタ／ロック／一括売却）
 ├ 冒険者ごとに 武器1 + 防具1 を装備
 ├ 撤退ルールを選択（3種）
 ├ 派遣先ステージを選択
 └ 派遣（初期2人まで同時）
        ↓ アプリを閉じてよい
【派遣中】実時間で進行。オフライン上限8時間
        ↓ 完了通知
【帰還】結果は3種
 ├ 撤退成功 → 戦利品を全て持ち帰り、装備も残る
 ├ ステージクリア → 戦利品＋ステージ突破
 └ 死亡 → 戦利品全ロスト、装備2点が消滅（冒険者本人は無事に帰る）
```

### 4.2 冒険者（3職・成長しない）

冒険者は**成長せず、死亡しても失われない**。装備を失って手ぶらで帰るだけ。
職業は固定の器であり、レベルもステータス成長も持たない。

| 職 | HP | 装備制限 | 特性 |
|---|---|---|---|
| 剣士 | 100 | 制限なし | 基準値。補正なし |
| 重装兵 | 140 | 重防具のみ装備可 | 被ダメージ -20%／ステージ所要時間 +15% |
| 遊撃兵 | 70 | 軽防具のみ装備可 | 回避 +15%／ステージ所要時間 -20%／ドロップ +1個 |

**初期は剣士1人。ステージ3クリアで2人目、ステージ6クリアで3人目を解放。**

### 4.3 撤退ルール（3種）

| ルール | 挙動 |
|---|---|
| 深追い | HP0まで戦う。最深到達だが死亡リスク最大 |
| 標準 | HP30%を切った時点で帰還 |
| 慎重 | HP50%を切った時点で帰還 |

撤退成功時、**その時点までの戦利品は全て持ち帰る**。

### 4.4 死亡時の救済

- 装備を全て失った場合、**最低性能の初期装備（攻撃力ベース値、アフィックス0）を無限に支給する**
- 広告リワードで「消滅する装備のうち1つを救出」できる（§8）

## 5. 装備パラメータ（このゲームの中核）

### 5.1 設計原則

**総ダメージ量（バジェット）は狭くしか揺らさず、配分と効果を大きく揺らす。**
新しい武器が古い武器の単純な上位互換になった時点で、このゲームは失敗である。

### 5.2 5層構造

| 層 | 内容 | ランダム幅 |
|---|---|---|
| L0 ベースタイプ | 武器：短剣／片手剣／両手剣／槍／弓／杖<br>防具：軽鎧／中鎧／重鎧 | 抽選のみ |
| L1 基礎値 | 攻撃力・攻撃速度・防御・会心率 | **±10%以内** |
| L2 属性配分 | 物理／炎／雷／毒 の比率 | 大きく振る |
| L3 アフィックス | 追加効果 0〜4枠（武器）／0〜3枠（防具） | 大きく振る |
| L4 ユニーク効果 | ルールを書き換える1行 | 稀（3%） |

### 5.3 L1 基礎値（アイテムパワー100の片手剣の例）

| 項目 | レンジ |
|---|---|
| 攻撃力 | 45〜55 |
| 攻撃速度 | 1.20〜1.32 回/秒 |
| 会心率 | 5.0〜7.0% |

**攻撃力と攻撃速度は逆相関にすること。** 片方が高ロールならもう片方が低ロールになる制約を入れ、
DPS総量が狭い範囲に収まるようにする。差はL2・L3で付ける。

### 5.4 L3 アフィックス（MVPは合計8種で開始）

**武器用**

| アフィックス | レンジ | 種別 |
|---|---|---|
| 攻撃力 +X% | 8〜15% | 純粋強化 |
| 会心ダメージ +X% | 15〜40% | 純粋強化 |
| 炎/雷/毒ダメージ追加 +X | 4〜12 | 属性寄せ |
| HP50%以下で威力 +X% | 20〜50% | **立ち回りが変わる** |
| 連続ヒットで速度 +X%（最大5回） | 3〜8% | **立ち回りが変わる** |

**防具用**

| アフィックス | レンジ | 種別 |
|---|---|---|
| 防御 +X% | 8〜15% | 純粋強化 |
| 属性耐性 +X% | 10〜30% | **敵構成に対応** |
| 撃破時にHP回復 +X | 2〜6（固定値） | **生存** |

**重要な制約：回復効果は防具側にのみ実装すること。** 武器に回復を付けてはならない。
回復量は割合ではなく固定値とし、深層のダメージインフレに自然と置いていかれる設計にする。
（回復付き武器が常に最適解になる破綻を防ぐため）

### 5.5 L4 ユニーク効果（例。3%で付与）

- 会心が発生しない。代わりに全攻撃の威力が常時上昇する
- 攻撃速度が半減し、1撃が3倍かつ範囲攻撃になる
- 敵を倒すたびに攻撃力 +1（そのステージ中のみ）
- ドロップ率 +50%、被ダメージ +25%

### 5.6 数値の表示（重要）

**内部では連続値を持ってよいが、画面には5段階のティアだけを表示すること。**

```
攻撃力 +8%  → ★☆☆☆☆
攻撃力 +15% → ★★★★★
```

`+11.3%` と `+11.7%` の差はプレイヤーにとって情報ではなくノイズである。

### 5.7 レアリティ（枠数で表現。数値の高さでは表現しない）

| レアリティ | アフィックス枠 | ユニーク | 出現率 | カットイン |
|---|---|---|---|---|
| 並 | 0 | なし | 60% | なし |
| 上質 | 1〜2 | なし | 28% | なし |
| **稀少** | 3〜4 | なし | 9% | **あり** |
| **遺物** | 2固定+ランダム1 | あり | 3% | **あり（強）** |

### 5.8 生成の擬似コード

```ts
function generateItem(itemPower: number, slot: Slot, rng: RNG): Item {
  const base = rng.pick(BASE_TYPES[slot]);
  const budget = itemPower * rng.range(0.95, 1.05);

  const speedRoll = rng.range(0, 1);
  const attack = budget * (1 - speedRoll * 0.25);
  const speed  = base.speed * (1 + speedRoll * 0.25);

  const element = rng.weighted(ELEMENT_SPLITS);
  const rarity  = rollRarity(rng);

  const affixes = rng.sampleWithoutReplacement(
    AFFIX_POOL[slot].filter(a => a.tags.some(t => base.tags.includes(t))),
    rarity.affixCount
  ).map(a => ({ ...a, tier: rng.tier() }));  // 5段階に丸める

  const unique = rarity.hasUnique ? rng.pick(UNIQUE_POOL) : null;
  return { base, attack, speed, element, affixes, unique, identified: false };
}
```

`AFFIX_POOL` を必ずベースタイプでフィルタすること。武器種ごとに引ける池が違うことが収集動機になる。

### 5.9 上限

- 攻撃力は**3桁（999）を上限**とする。4桁に到達する数値インフレを設計してはならない
- ステージ難易度は敵のHPと数で上げ、プレイヤー側の数値は999で頭打ちにする

## 6. 戦闘シミュレーション

### 6.1 構造

戦闘は**内部ターン制**で解決し、画面には一切描画しない。

```
simulate(seed, adventurer, weapon, armor, retreatRule, stage) => RunResult
```

`RunResult` は到達深度・戦利品配列・結果種別（撤退／クリア／死亡）・ハイライト3件を含む。

### 6.2 進行

- 1ステージは N 個の遭遇で構成される（N はステージごとに定義）
- 1遭遇あたりの実時間 = ステージ所要時間 ÷ N
- 1遭遇の敵数は 3〜5 体
- HPは**単調減少**する（自動回復なし。防具の撃破時回復のみ）

### 6.3 ダメージ式（基準。バランス調整は可、構造は変えない）

```
命中ダメージ = (攻撃力 × 属性係数 × (1 + アフィックス補正)) - 敵防御
会心時 = 命中ダメージ × 会心倍率
被ダメージ = (敵攻撃力 × (1 - 防御率) × (1 - 属性耐性)) × (1 - 職特性補正)
```

属性係数：敵の耐性属性なら 0.5、弱点属性なら 1.5、それ以外 1.0

### 6.4 敵の耐性表示

**出撃前のステージ選択画面で、そのステージの敵の属性傾向をアイコンで明示すること。**
プレイヤーが装備を選ぶ唯一の手がかりであるため、隠してはならない。

## 7. ステージとレポート

### 7.1 ステージ構成（全10）

| # | 名称 | 所要時間 | 敵属性 | 有効属性 | ドロップ傾向 |
|---|---|---|---|---|---|
| 1 | 廃坑 | 5分 | 物理 | ー | 武器寄り |
| 2 | 苔の回廊 | 10分 | 毒 | 炎 | 防具寄り |
| 3 | 灼熱坑 | 20分 | 炎 | 雷 | 武器寄り |
| 4 | 氷結層 | 40分 | 氷 | 炎 | 均等 |
| 5 | 雷鳴洞 | 60分 | 雷 | 毒 | 武器寄り |
| 6 | 腐界 | 90分 | 毒 | 炎 | 防具寄り |
| 7 | 溶岩回廊 | 120分 | 炎 | 氷 | 均等 |
| 8 | 骸の間 | 180分 | 物理 | 雷 | 武器寄り |
| 9 | 深層祭壇 | 300分 | 複合 | ー | 高レア率 |
| 10 | 深淵 | 480分 | 複合 | ー | 最高レア率 |

- 各ステージ末にボスを配置する
- クリア後も再挑戦可能（周回して装備を稼ぐ前提）
- ステージ10クリアで**難易度+1**、全ステージが再解放される（無限ティア）
- ステージ解放には金を消費する（§7.5）

### 7.2 オフライン進行

- **上限8時間。** それを超えた分は進行しない
- 端末時刻の**巻き戻しを検知**すること（前回保存時刻より過去なら進行量ゼロ）
- 帰還時にローカル通知を送る

### 7.3 帰還レポート

| 要素 | 内容 |
|---|---|
| 結果1行 | 「深度23で撤退／ボス『石の番人』撃破」 |
| **見どころ3行** | 装備選択の答え合わせ。例：「炎耐性の敵に炎武器で挑み、火力が半減していた」 |
| 到達深度 | 縦断面グラフ（v1資産の静止画転用） |
| 戦利品 | 未鑑定品を最大10個 |

**見どころ3行が最重要。** なぜその結果になったかが分からないと、完全な運ゲーに感じられる。
シミュレーション中に「最も大きなダメージ要因」「最も効いたアフィックス」「敗因」を
記録して出力すること。

### 7.4 開封

- **一括開封。** ボタン1つで10個を順次開ける
- 並・上質は流れるように表示
- **稀少以上でカットインを挿入**（v1のレアホールド演出を転用、強度を上げる）
- 遺物はさらに強い演出（画面暗転＋ユニーク効果のテキスト表示）
- 図鑑には「初回入手」「どのステージで出たか」を記録する

### 7.5 金の使い道（3つのみ）

| 用途 | 内容 |
|---|---|
| 派遣枠の拡張 | 2人目・3人目の解放コスト（ステージクリアと併用） |
| ステージ解放 | 次のステージへ進むための費用 |
| 再鑑定 | アフィックス1つをランダムに振り直す |

不要装備は**売却可能**。ゴミ装備が金に変わらないと純粋なストレスになるため必須。

## 9. 見た目

**この節は `docs/UI-SPEC.md` に全面差し替えた。**

three.js による全面移行にともない、当初のドット絵前提の規約
（Canvas 2D 限定・内部解像度360×640の整数倍スケール・ビットマップフォント・
パレット32色・bloom禁止）はすべて破棄した。

差し替えの理由は `docs/UI-SPEC.md` §0 に記載している。要点だけ再掲する。

- このコードは生成AIが書く。選ぶべきは「人間が書きやすいUI」ではなく
  「**生成AIが正しく書けて、正しさを機械的に確かめられるUI**」である
- 移行前の canvas 実装には手計算の座標式が298箇所あり、実際に出た不具合は
  そのほぼ全部がレイアウトを算術で解いていたことに起因していた
- canvas は目視でしか検証できないが、DOM は表明で検証できる。
  視覚的QAが自動テストに変わる

新しい規約の骨子:

| 項目 | 指定 |
|---|---|
| 描画 | three.js（World層）＋ DOM/CSS（Interface層）の2層 |
| three.js の責務 | 奥行き・光・霧・粒子**のみ**。文字と当たり判定を置かない |
| DOM の責務 | 文字・数値・操作の**すべて** |
| 解像度 | 内部解像度の概念を廃止。`100vw × 100vh` と `dvh` で組む |
| 検証 | レイアウトの正しさは DOM の表明で確かめる（UI-SPEC §7.1 の U1〜U10） |

詳細（画面・コンポーネント・トークン・状態・性能予算・検証項目の全指定）は
`docs/UI-SPEC.md` を参照。

## 10. サブエージェント分割とベンチマーク

**各担当には比較対象となる実在作品を割り当てる。** 担当は自分の成果物を
「よくできているか」ではなく「**割り当てられた作品と並べて劣っていないか**」で判断すること。

| # | 担当 | 成果物 | ベンチマーク | 比較する観点 |
|---|---|---|---|---|
| 1 | 資産整理 | §1の流用・削除の実行 | ー | デッドコードが残っていないこと |
| 2 | シミュレーション | `sim/` 一式、オフライン再計算、リプレイ再現 | Melvor Idle | オフライン計算の正確さと軽さ |
| 3 | 装備生成 | §5 の全実装、生成テーブル | Diablo系／Loop Hero | ドロップ1個1個に個性があるか |
| 4 | 派遣UI | 冒険者カード、装備選択、撤退ルール、ステージ選択 | Melvor Idle | 3判断が1画面で完結するか |
| 5 | インベントリ | ソート／フィルタ／ロック／一括売却／比較表示 | Path of Exile | 200個所持時の管理しやすさ |
| 6 | 開封演出 | 一括開封、稀少カットイン、遺物演出 | Balatro | 数値と演出が跳ねる瞬間の快感 |
| 7 | レポート | 結果1行、見どころ3行、深度グラフ、図鑑 | Idle Slayer | 何が起きたか3秒で分かるか |
| 8 | ドット絵 | 新規スプライト、UI枠 | 勇者のくせになまいきだ。 | 1px精度、パレット統一 |

担当外のファイルを書き換えないこと。

## 11. 批評ループ

各担当とは**別のエージェント**を批評役として立てること。実装者に自己採点をさせない。

### 11.0 批評役の人格と義務

- **極めて辛口であること。褒めることを目的にしない。** 「良くなっています」「十分な品質です」
  といった評価だけを返すのは職務放棄とみなす
- 指摘は必ず**具体的**であること。「もっと洗練させるべき」は不可
- 実装者の努力や進捗に配慮しないこと。判断材料は**出力された画面と挙動のみ**

### 11.0.1 参照画像の準備（A軸の前提条件）

**ブラインド比較は、比較対象の実物を用意しない限り機能しない。**
記憶にある印象と比べた「つもり」の報告は無効とする。

各担当は着手前に、ベンチマーク作品の**スクリーンショットを最低3枚**ユーザーに要求すること。
用意されなかった場合、**A軸の判定は成立しないため、その旨を必ず未達リストに記載する**。
勝手に「比較の結果、遜色ない」と報告してはならない。

### 11.1 A軸：見た目

- 実装画面のスクリーンショットと参照画像を**ブラインドで並べて比較**し、どちらが優れているか宣言させる
- 「良い」ではなく「**どこがどう劣っているか**」を必ず3点以上、具体的に指摘させる

### 11.2 B軸：手触り

**20回派遣を繰り返し**、以下を数値で報告させる。

| 指標 | 不合格ライン |
|---|---|
| 装備選択に迷わなかった回数 | 20回中10回以上（＝最適解が固定化している） |
| 開封が作業に感じた回数 | 1回でもあれば不合格 |
| 結果の理由が分からなかった回数 | 0でなければ不合格 |
| 「この武器いいな」と思えた回数 | 20回中5回未満なら不合格 |
| インベントリ整理が苦痛だった回数 | 1回でもあれば不合格 |

### 11.3 C軸：破綻検査

**1つでも該当したら即不合格。**

| # | 破綻パターン | 検出方法 |
|---|---|---|
| C1 | ~~ドットがにじむ／ずれる~~ | **廃止**（three.js移行で消滅）。代わりに `docs/UI-SPEC.md` §7.1 の U1〜U10 を用いる |
| C2 | `Math.random()` が `sim/` に混入 | 全文検索。1件でも不合格 |
| C3 | 同条件で結果が変わる | 同一seed・同一装備で100回実行し全一致を確認 |
| C4 | オフライン計算が実時間経過と一致しない | 8時間分を一括計算した結果と、分割計算の結果が一致するか |
| C5 | 端末時刻の巻き戻しで進行する | 時計を過去に戻して進行量ゼロを確認 |
| C6 | `sim/` が Canvas / DOM を import している | import文の静的検査 |
| C7 | 特定の武器・防具の組み合わせが常に最適 | 全組み合わせで平均到達深度を算出。1位が2位を20%以上引き離したら不合格 |
| C8 | 攻撃力が4桁に到達する | 上限999のクランプを確認 |
| C9 | 回復アフィックスが武器側に存在する | データ定義の検査 |
| C10 | 200個所持時にインベントリ操作が1秒以上かかる | 実機計測 |
| C11 | 破棄したはずのv1コードが残存 | §1.2 の各項目をgrep |

### 11.4 合格ライン

```
A軸：ブラインド比較で5割以上の勝率（参照画像がある場合のみ有効）
B軸：§11.2 の全指標が不合格ラインに達していないこと
C軸：C1〜C11 すべて非該当
```

### 11.5 ラウンドの運用手順

```
① 担当エージェントが実装する
② 批評エージェントがA/B/C軸で判定し、劣っている点を最低3件、具体的に列挙する
③ 担当エージェントが全項目に「直した／直さない（理由）」を1件ずつ返す
④ 批評エージェントが再判定する
```

**②で指摘が3件未満だった場合、批評が甘いとみなして批評エージェントを立て直すこと。**

### 11.6 ループ上限

**最大4ラウンド。** 4ラウンド終了時点で未達の項目は無理に直さず、
**未達リストとして正直に報告すること。** 未達リストなしの完成宣言は認めない。

```
| 項目 | 軸 | 現状 | 未達の理由 | 残作業の見積 |
```

## 13. 完成の定義

1. ステージ1〜10をクリアし、難易度+1の周回に入れる
2. 60fps を維持している
3. 同一seed・同一装備・同一撤退ルールから、同じ結果が完全に再現される
4. オフライン8時間の計算結果が、分割計算の結果と一致する
5. `sim/` が Canvas / DOM に一切依存していない
6. §1.2 の破棄対象がリポジトリに残っていない
7. §11 の合格ラインを満たしている、**または未達リストが提出されている**

---

## 14. 実装順序

**① §1 の資産整理 → ② 装備生成システム（§5）→ ③ 開封演出（§7.4）**

この3つを最初に通し、**「10個開封して1個嬉しいものが出るか」だけを検証**すること。
このゲームの面白さは全てここに集約されており、ここが成立しなければ
派遣UIもステージもインベントリも作る意味がない。

拠点UI・ステージ・オフライン進行は、開封の検証が通ってから着手する。
