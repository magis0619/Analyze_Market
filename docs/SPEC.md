# OUTFITTER（仮題）— Claude Code 向け実装指示書

## 0. このドキュメントの読み方

これは MVP の仕様書です。**「§2 コア体験」と「§7 批評ループ」は絶対に省略しないこと。**
仕様に書かれていない機能を親切心で追加しないこと。迷ったら §8 のスコープ表に従う。

### 判定の原則（全工程に適用）

1. **「AAA品質」「良い感じ」「洗練された」といった抽象語で品質を判定してはならない。**
   判定は常に、§6 で各担当に割り当てられた**実在するベンチマーク作品との比較**で行う。
2. **実装したエージェントに自己採点をさせない。** 品質判定は必ず別のエージェントが行う（§7）。
3. **完成の宣言は、未達リストの提出とセットでのみ認める。**「完璧です」という報告は、
   未達リストが添えられていない限り無効として差し戻す。

## 2. コア体験（最優先・妥協禁止）

> **プレイヤーは一度もダンジョンに潜らない。店から出られない。**
> できるのは「客を読み、装備を見立てて、送り出し、見守る」ことだけ。

このゲームで気持ちいい瞬間は戦闘ではなく、**観戦中に「渡しておいた装備のおかげで選択肢が開く」瞬間**である。
以下のどれか一つでも崩れたら仕様違反とみなすこと。

- プレイヤーが直接戦闘を操作できるようにしてはいけない
- プレイヤーがダンジョン画面で自由に移動できるようにしてはいけない
- 装備を渡していないのに有利な選択肢が出てはいけない

## 3. ゲーム仕様

### 3.1 1サイクルの構成（約100秒）

| フェーズ | 秒数 | 内容 |
|---|---|---|
| 商談 | 30秒 | 客カード表示 → 質問1回 → 装備を3点まで見立てて渡す |
| 見送り | 3秒 | 冒険者が退店。天秤アニメで成功見込みを暗示（数値は出さない） |
| 観戦 | 50〜70秒 | 縦断面ダンジョンを降下。20秒に1回、計3回の選択が発生 |
| 結果 | 10秒 | 到達深度の確定、戦利品の納品、装備の消耗・喪失 |

### 3.2 商談フェーズ

客カードに表示する項目：

```
名前 / 職業 / Lv / 所持金 / 今回の依頼（目標深度） / 性格
```

**「性格」は初回は黒塗り。** 会話で1つだけ質問でき、その回答で黒塗りが開く。
質問の選択肢は3つ（「得意な戦い方は？」「前回はどこで死にかけた？」「何を持って帰りたい？」）。
どれを聞くかで開示される情報が変わる。全部は聞けない。

**性格3種（プレイヤーの選択を制限する装置）**

| 性格 | 観戦フェーズでの効果 |
|---|---|
| 臆病 | 深度5以降、HPが半分を切ると**自動で撤退する**。プレイヤーは止められない |
| 強欲 | 鉱脈イベントが出ると**必ず掘る**。時間を消費し、その分だけ深く潜れない |
| 短気 | 「逃げる」の選択肢が**選べない（グレーアウト）** |

装備は棚から**最大3点**。在庫は有限で、渡した装備はそのランの間は戻らない。

### 3.3 観戦フェーズ

**表示**：画面を縦に切った地層の断面図。冒険者のドットが上から下へ降下する。
画面右端に細いイベントログ（1行ずつ流れる）。画面左端に深度メーター。

**進行**：自動。プレイヤーの操作は選択が発生したときのみ。
選択は1ラン中3回。制限時間5秒、無選択なら安全側の選択肢が自動で選ばれる。

**選択肢の生成ルール（最重要）**

```
選択肢 = 常時選択肢（1〜2個） + 装備によって開く選択肢（0〜2個）
```

装備が条件を満たすときだけ、追加の選択肢が現れる。UI 上、装備由来の選択肢には
**どの装備が根拠になっているかアイコンで表示する**（因果をプレイヤーに理解させるため）。

### 3.4 結果フェーズ

- **生還**：到達深度がスコアとして確定。持ち帰った戦利品の一部が店に納品され、次回以降の在庫になる
- **死亡**：渡した装備は永久に失われる。その冒険者は**二度と来店しない**
- どちらの場合も、手紙形式で**敗因・成功要因を1行で明示する**（例：「重量超過により崩落を回避できず」）

納品された戦利品は図鑑に登録され、**誰が持ち帰ったか**が記録される。

### 3.5 常連と世代交代

同じ冒険者が繰り返し来店し、生還のたびにレベルが上がって依頼深度が深くなる。
MVP では**常連1人を最大6ランまで追う**。死亡でその系譜は終了し、
弟子または子が遺品を1つ持って来店する（＝次の系譜の開始）。

## 4. アーキテクチャ要件（重要）

**ダンジョン攻略は「決定論的シミュレーション」として実装し、観戦画面はその再生に徹すること。**

```
simulate(seed, adventurer, equipment[], choices[]) => DungeonEvent[]
```

- 観戦画面は `DungeonEvent[]` を時間軸に沿って再生するだけ。ロジックを持たせない
- 選択が発生したら、その時点から再シミュレートする
- 1ランの結果は `seed + 装備ID配列 + 選択履歴` だけで完全再現できること（リプレイデータは数十バイト）

この分離を守ること。将来の日替わりランキング・他プレイヤーの攻略観戦・非同期対戦を、
サーバをほぼ持たずに追加できるかどうかが、この設計にかかっている。
**シミュレーションと描画を混ぜて書いた場合、実装のやり直しを指示する。**

ディレクトリ構成の例：

```
src/
  sim/        # 決定論シミュレーション。Canvas を一切 import しない
  render/     # 描画専用。sim の結果を受け取るだけ
  ui/         # 商談・選択UI
  data/       # 装備・イベント・冒険者のマスタ（JSON or TS定数）
```

## 5. ビジュアル指示

### 5.1 方向性

**参考：『勇者のくせになまいきだ。』のドット絵。** 断面図で地層を掘り進む画面構成、
太めのアウトライン、少ない色数で情報を成立させる潔さ、キャラの2〜4フレームの
コミカルな動きを参考にする。

**重要：既存作品のアセットを流用・複製してはならない。** 参考にするのは表現の方向性のみで、
ドット絵はすべて新規に生成すること。キャラクターデザインや地形の意匠も既存作品に
似せないこと。

### 5.2 具体的な数値指定

| 項目 | 指定 |
|---|---|
| 内部解像度 | 360×640 で描画し、整数倍スケールで画面に拡大 |
| キャラクター | 16×16px |
| 地形タイル | 16×16px |
| アイテムアイコン | 16×16px |
| フォント | ビットマップフォント（8×8 または 8×12）。TrueType のアンチエイリアス表示は禁止 |
| パレット | 全体で32色以内。地層ごとに8色のサブパレットを割り当てる |
| アウトライン | キャラ・アイテムには1px の暗色アウトラインを必ず入れる |
| アニメーション | 歩行4フレーム、採掘2フレーム、被弾1フレーム（点滅） |

### 5.3 禁止事項

- `imageSmoothingEnabled = true`（必ず false）
- 非整数倍のスケーリング
- ドットの回転（スプライトは反転のみ許可）
- ドット絵と噛み合わないポストエフェクト（bloom、ブラー、グラデーションのオーバーレイ）
- 1画面に3種類以上のフォントサイズ

### 5.4 演出のメリハリ

平常時は淡々と進行させ、**次の3つの瞬間だけ画面を止めて寄る**こと。

1. レア戦利品を掘り当てた瞬間（0.8秒のホールド＋パーティクル）
2. 装備由来の選択肢が開いた瞬間（該当装備アイコンが1回光る）
3. 冒険者が死亡した瞬間（画面停止1.2秒、色を落とす）

## 6. サブエージェントによる分割

以下の単位で並列に実装すること。担当外のファイルを書き換えないこと。

**各担当には、比較対象となる実在作品を1つずつ割り当てる。** 担当エージェントは自分の担当箇所を
「よくできているか」ではなく「**割り当てられた作品と並べて劣っていないか**」で判断すること。

| # | 担当 | 主な成果物 | ベンチマーク作品（比較対象） | 比較する観点 |
|---|---|---|---|---|
| 1 | シミュレーション基盤 | `sim/` 一式、PRNG、イベント解決、リプレイ再現テスト | Slay the Spire | シード再現の完全性、リプレイデータの軽さ |
| 2 | データ設計 | `data/` の装備12種・イベント15種・冒険者・性格の定義 | Loop Hero | 装備とイベントの噛み合いの density |
| 3 | 商談フェーズ | 客カード、質問UI、棚からの見立てUI、重量判定 | Papers, Please | カウンター越しに1件ずつ捌く緊張感と情報密度 |
| 4 | 観戦フェーズ | 縦断面の描画、降下、深度メーター、イベントログ | 勇者のくせになまいきだ。／Dome Keeper | 断面図1画面あたりの情報量と読み取りやすさ |
| 5 | 選択UI | 選択肢の生成表示、装備アイコンによる根拠表示、5秒タイマー | Reigns | 選択の因果が一目で分かるか |
| 6 | ドット絵アセット | キャラ・地形・アイテム・UI枠の全スプライト | 勇者のくせになまいきだ。 | 1px単位の精度、パレット統一、アウトラインの一貫性 |
| 7 | 演出 | §5.4 の3演出、SE、画面遷移 | Balatro／Vampire Survivors | 数値が跳ねる瞬間・レア発見の手応え |

## 7. 批評ループ

各担当とは**別のエージェント**を批評役として立てること。実装者に自己採点をさせない。

### 7.0 批評役の人格と義務

- **極めて辛口であること。褒めることを目的にしない。** 「良くなっています」「十分な品質です」
  といった評価だけを返すのは職務放棄とみなす
- 指摘は必ず**具体的**であること。「もっと洗練させるべき」は不可。
  「深度メーターの数字が8pxフォントで、地層の背景色と近く読めない」なら可
- 実装者の努力や進捗に配慮しないこと。判断材料は**出力された画面と挙動のみ**

### 7.0.1 参照画像の準備（A軸の前提条件）

**ブラインド比較は、比較対象の実物を用意しない限り機能しない。**
記憶にある印象と比べた「つもり」の報告は無効とする。

各担当は着手前に、§6 で割り当てられたベンチマーク作品の**スクリーンショットを最低3枚**、
ユーザーに要求すること。用意されなかった場合、**A軸の判定は成立しないため、
その旨を必ず未達リストに記載すること**（勝手に「比較の結果、遜色ない」と報告しない）。

### 7.1 A軸：見た目

- 実装画面のスクリーンショットと、参考にしたドット絵ゲームの画面を**ブラインドで並べて比較**し、
  どちらが優れているかを宣言させる
- 「良い」ではなく「**どこがどう劣っているか**」を必ず3点以上、具体的に指摘させる
- チェック項目：1px単位のズレ、パレットの統一、可読性、アウトラインの一貫性、
  ドットのにじみ（スケーリング事故）

### 7.2 B軸：手触り

- 実際に**10ラン連続でプレイ**し、以下を数値で報告させる
  - スキップしたくなった回数（**1回でもあれば不合格**）
  - 選択肢が出た理由が分からなかった回数（0でなければ不合格）
  - 装備を渡す判断に迷わなかった回数（＝最適解が固定化している兆候）
  - 「渡しておいてよかった」と思えた回数（10ラン中5回未満なら不合格）

### 7.3 C軸：破綻検査

以下は**1つでも該当したら即不合格**。ラウンドを消費してでも最優先で潰すこと。

| # | 破綻パターン | 検出方法 |
|---|---|---|
| C1 | ドットがにじむ／ずれる | 実機スクショを400%拡大し、1pxの半端が出ていないか目視 |
| C2 | `Math.random()` が `sim/` に混入 | 全文検索。1件でもあれば不合格 |
| C3 | 同じ seed と選択履歴で結果が変わる | 同条件で100回実行し、全て一致するか自動テスト |
| C4 | 60fps を割る | 観戦フェーズ全体でフレームタイムを計測。16.7ms超が全体の1%以上なら不合格 |
| C5 | `sim/` が Canvas / DOM を import している | import 文の静的検査 |
| C6 | 装備を渡していないのに有利な選択肢が出る | 装備0点で10ラン実行し、装備由来の選択肢が0件であることを確認 |
| C7 | 特定の3点セットが常に最適 | 全組み合わせで平均到達深度を算出。上位1セットが2位を20%以上引き離したら不合格 |
| C8 | 初回ロードが3秒を超える | 実機で計測 |

### 7.4 合格ライン

```
A軸：ブラインド比較で5割以上の勝率（参照画像が用意されている場合のみ有効）
B軸：スキップ欲求ゼロ、因果の不明瞭ゼロ、「よかった」5回以上／10ラン
C軸：C1〜C8 すべて非該当
```

### 7.5 ラウンドの運用手順

1ラウンドは以下の4手順で構成する。手順を飛ばさないこと。

```
① 担当エージェントが実装する
② 批評エージェントがA軸・B軸・C軸で判定し、劣っている点を最低3件、具体的に列挙する
③ 担当エージェントが、列挙された全項目に対して「直した／直さない（理由）」を1件ずつ返す
④ 批評エージェントが再判定する
```

**②で指摘が3件未満だった場合、批評が甘いとみなして批評エージェントを立て直すこと。**

### 7.6 ループ上限

**最大4ラウンド。** 4ラウンド終了時点で未達の項目は、無理に直さず
**「未達リスト」として正直に報告すること。** 完成を宣言する前に必ず未達リストを出力する。
未達リストなしの完成宣言は認めない。

未達リストの形式：

```
| 項目 | 軸 | 現状 | 未達の理由 | 残作業の見積 |
```

| 入れる | 入れない |

## 9. 完成の定義

以下を全て満たしたときのみ完成とみなす。

1. 常連1人を6ランまで追い切れる（死亡による系譜終了まで含む）
2. 60fps を維持している
3. 同じ seed と選択履歴から、同じ結果が完全に再現される
4. §7 の A軸・B軸の合格ラインを満たしている、または**未達リストが提出されている**
5. `sim/` が Canvas に一切依存していない

## 10. 実装の順序

**§4 のシミュレーション基盤と、§5.4 の「レア発見」演出を最初に作ること。**

このゲームは「自分が戦わないので快感が全部間接になる」という構造的リスクを抱えている。
その検証は演出の質にかかっており、後回しにすると手戻りが最大化する。
商談UIや図鑑よりも先に、**観戦画面で1回だけレアを掘り当てる**ところまでを動かし、
そこで面白さが成立するかを確認してから残りに着手すること。
