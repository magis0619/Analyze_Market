# iOS 版の採点

`docs/IOS-RUBRIC.md` の基準で採点する。**満点でなかった項目は必ず理由を書く。**
「だいたい良い」は 0 点として扱う。

機械が測る項目は `ios/Tools/audit.sh`（XCUITest）と `ios/Tools/pixels.py`（画素）が出す。
目視の項目は、なぜその点かを1行で書く。

### このラウンドで直したこと

- **露出。** ブルームの閾値が低く、加算合成の光の玉が全部にじみに乗って画面ごと白く飛んでいた。
  閾値 0.75 → 0.92、強度 0.9 → 0.45、露出 -0.35。薬草園は 5.69% → 0.00%。
- **セグメントをやめて 44pt のタブを自作。** iOS の `segmented` は 32pt で、
  自分で決めた基準を満たさない。基準を曲げるより部品を作った。
- **名札をアイコンのチップに。** 幅の広い名札を5つ横に並べると 402pt に収まらず必ず重なる。
  何であるかは 3D の物that自体が言っているので、チップは「押せる」と件数だけを言う。
- **チップを板より上に置いた。** 下に置くと `ScrollView` がタップを飲む。
  XCUITest の `isHittable` は要素自身の可視性しか見ないので「押せる」と報告されるが、
  実際には押せない——**スクショにも出ない、最も気づきにくい壊れ方**だった。
- **看板がカメラの外にいた。** x=-7.6 は画角の外で、投影が返らず名札が出ていなかった。

### 検査そのものの欠陥も2つ直した

- 入れ子（タブの中のタブ）を重なりとして数えていた。
- `ScrollView` の外にある要素まで「押せない」と数えていた。スクロールすれば届くものを
  欠陥にすると、本物の欠陥が埋もれる。

## ラウンド2 — 採点が成立しなかった

ラウンド2の変更（触覚・図鑑の書庫・入口と工房の作り直し）を入れて撮り直したのに、
画素の数字がほとんど動かなかった。**古いアプリを撮っていた。**
`shots.sh` はシミュレータに入っている物をそのまま起動していて、
ビルドした物を入れ直していなかった。図鑑には作ったはずの書庫ではなく、
前の版の展示台が映っていた——「直したのに直っていない」ではなく「直した物を見ていない」。

採点が無効なので表は作らない。直したのは道具のほう:

- `shots.sh` が**必ずビルドして入れ直してから**撮るようにした。
- 真っ黒な画を撮ったら撮り直すようにした。入れ直し直後の初回起動は遅く、
  待ち 2.2 秒では起動前を撮っていて、9画面ぶんが「暗すぎ」の採点表になった。
- 待ちを 3 秒 → 5 秒に。シーンは明るさを目標値へ滑らかに寄せるので、途中で撮ると
  暗い絵が写る（派遣準備が平均輝度 12.0 と誤判定され、直したばかりの入口を疑った）。
- `pixels.py` が採点する画面を名指しにした。glob だと、あとで切り出した画像まで
  「画面」として表に混ざっていた。

**「直したのに数字が変わらない」は、たいてい古い物を見ている。**

## ラウンド3

**（点数は下の表。先に、この採点そのものについて）**

### ラウンド1の 56 点も間違っていた

ラウンド1で **A2（コントラスト 4.5:1）を 5/5 と書いた。測っていなかったのに。**
根拠にしたのは「トークンの色の組み合わせは web 版で検査済み」ということだけで、
それが守るのは**板の上の文字だけ**だった。3D の上に直に置いた文字は背景が
毎フレーム変わるので、トークンでは何も保証できない。

このラウンドで、スクリーンショットの画素から実際にコントラストを測る検査を足したら、
**6画面で 26 件の読めない文字**が出た。タイトルの副題は明るい小屋の壁の上で 1.6:1、
所持品の副文は展示台の紫の光を透かして 2.3:1。ラウンド1の 56 点は、
**測っていない項目を満点にした 56 点**だった。

**点は、検査が正しい範囲でしか正しくない。** この文書に並ぶ数字も同じ条件つきで読むこと。

### 26 件はどれも同じ原因だった

1つずつ直しても意味がないので、根の3つを直した。

- **`DS.faint` が 0x626C86 で、一番暗い背景に置いてなお 3.80:1。**
  つまり注記は全部、どこに置いても本文としては読めていなかった。0x7A849E へ。
- **素材（`ultraThinMaterial`）の板が背景の明るさをそのまま受けていた。**
  `Surface` を作って、素材の下に必ず地の色を敷くようにした。素材は残す——
  iOS らしい奥行きはそこから来るので、消すのではなく明るさだけ渡さないようにする。
- **`.opacity(0.55)` で「作れない」を表していた。** 札ごと薄くすると、
  一番読ませたい「材料不足」という理由が一番読めなくなる（2.3:1）。
  薄くするのをやめ、理由は `DS.down` で言うようにした。

変異で確かめた: `faint` を元の色に戻すと A2 が地図の4件で鳴る。空振りの検査ではない。

### 3D で2回、同じ間違いをしていた

**物のほうが画面より大きかった。** 縦画面の水平半幅は `距離 × tan(縦FOV/2) × 0.46`
しかない。大鍋は半径 3.8 に対して半幅 3.0、入口の岩の輪は半径 5.4 に対して半幅 2.6。
どちらも「床も棚も作ったのに、黒い帯と淡い楕円しか映らない」という壊れ方で、
**スクショを見ても何が足りないのか分からない**。
`visibleHalfWidth(fov:distance:)` を置いて、勘ではなく計算で確かめるようにした。

大鍋にはもう1つあった。鍋だけを 0.55 倍にしたのに、液面を鍋の**外**に置いていたので、
原寸のままの液面が縮んだ鍋を手前から隠していた。

### 目視だった項目を2つ、測れる形にした

- **D4（演出が待たせすぎないか）。** ここは**測れなかった**。下に書く。
- **C4（滑らかさ）。** 体感で 4/4 と書いていた。`-fps` を足して統計を出し、
  拠点・薬草園・派遣準備の3つで **60fps** を確認した。ただし**シミュレータの数字**で、
  実機ではない。だから満点にはしない。

#### D4「演出中も操作を奪わない」は、測れないと分かった

書いた直後は 6/6 で通っていた。**通っていたが、何も見ていなかった。**
変異（開封の主要動線を演出中だけ `disabled` にする）を当てても素通りする。
3通り試して、3通りとも捕まえられなかった:

1. **起動してから問い合わせる。** 起動だけで数秒かかり、0.55 秒の演出はとっくに終わっている。
2. **`isEnabled` も見る。** `isHittable` は「その点に指が届くか」しか見ず、
   押しても何も起きないボタンでも true を返す——これ自体は本当の欠陥で直したが、
   変異は依然として捕まらなかった。
3. **動いているアプリの中で叩いて、待たずに問い合わせる。**
   `tap()` は**アプリが静止するまで返らない**。XCUITest は演出の完了を待ってから
   次へ進むので、問い合わせが演出の途中に落ちること自体が起きない。

つまり**この道具では観測できない**。測れないものを「測った」とは書かないので、
検査の名前を `test着いた直後に主要動線が使える` に変え、見ている内容もそこまでに縮めた。
演出の長さ（すべて 0.8 秒以内）と入力を塞いでいないことは、コードを読んで確かめている。

縮めた検査にも値打ちはあった。**3D に入れた `assert` が図鑑を落としていたのを、
これが見つけた。** 棚の列に「画角に収まっているか」の確認を掛けたが、
壁として端まで続いていてよい物にそれを掛けたのが間違いで、デバッグ実行の図鑑が
起動と同時に落ちていた。検査は「主要動線が現れない」と正しく言っていて、
最初それを検査の気まぐれだと思ったのはこちらの読み違いだった。

**新しい検査は、一度落ちるところを見るまで検査ではない。**
このラウンドで同じ形の間違いを3回した——A2 を測らずに満点にし、古いアプリを撮り、
落ちようのない検査を通した。どれも「緑だが何も見ていない」だった。

**C2** も1画面（拠点）だけの検査だった。崩れるのは横に詰めてある一覧や升目のほうなので、
9画面すべてを特大の文字で見るようにした。


#### 検査を広げたら、また2件出た

「着いた直後に主要動線が使えるか」を3画面から**9画面すべて**に広げたところ、
2件落ちた。どちらも本物だった。

- **所持品には `cta` が無かった。** 主要動線に `bulk` という名を付けていたせいで、
  B1（主要動線が1つ、親指の届く場所にあるか）は
  `if cta.exists` に囲まれて**所持品を一度も見ないまま通っていた**。
  名前を `cta` に直し、B1 は「無いなら無いと言う」形に変えた（`if` を外した）。
- **錬金工房は着いた時点で主要動線が死んでいた。** 何も選んでいないと
  「作る薬を選ぶ」という押せないボタンが1つあるだけの画面になる。
  作れる薬があるならそれを選んだ状態で始めるようにした。

`if 〜.exists` で囲むと、「その画面にそれが無い」が**失敗ではなく沈黙**になる。
このラウンドで見つけた「緑だが何も見ていない」4件のうち、2件はこの形だった。

### この基準が測っていないこと

ユーザーの依頼は「いい感じかどうか」だった。**この 100 点にその項目は無い。**

D1〜D4 が測るのは「画面ごとに違う場所に見えるか」「文字を邪魔しないか」
「状態が読めるか」「待たせないか」で、どれも**壊れていないこと**の確認でしかない。
絵として良いかは1点も配点していない。だから満点に近い数字が出ても、
それは「いい感じ」の証明にはならない。

基準は作る前に決めたので、後から項目を足して点を動かすことはしない。
代わりに、基準を満たしていてなお弱いと思うところを書いておく:

- **図鑑の書庫**は棚が横縞に見える。奥行きが読めるほどには組めていない。
- **錬金工房**は部屋に物が少なく、大鍋が置いてあるだけの空間になっている。
- **派遣準備の入口**は「岩の裂け目」までは行ったが、坑道の口には見えていない。
- **開封の光**は縦の帯で、Balatro を参考にしたときの「奔流」には届いていない。

これらは `docs/UNRESOLVED.md` にも同じことを書いた。
