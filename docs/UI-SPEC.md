# DELVERS UI 仕様書

three.js 全面移行にともなう UI の全指定。
`docs/SPEC.md` §9（見た目）を**この文書で差し替える**。ゲームの機能・数値・シミュレーションは
`docs/SPEC.md` の §1〜§8 と §12〜§14 が引き続き有効で、変更しない。

## 0. なぜこの構成にするか

### 0.1 前提: このゲームのUIは生成AIが書く

このプロジェクトのコードは実質すべて Claude Code が書いている。したがって
「人間が書きやすいUI」ではなく「**生成AIが正しく書けて、かつ正しさを機械的に確かめられるUI**」
を選ぶべきである。以下はその観点で選定した根拠。

### 0.2 実測: 現行の canvas 実装で何が起きていたか

移行前のコードを数えた結果。

| 項目 | 件数 | 内容 |
|---|---|---|
| 手計算の座標式 | **298** | `x + 24`, `Math.floor((w - tw) / 2)` のような、レイアウトを算術で解く式 |
| 折り返し・幅測定の自前実装 | **40** | `wrapText` / `textWidth` の呼び出し。行頭禁則も自前 |
| 当たり判定の手書き | **45** | `px >= x && px < x + w` の類 |

そしてこのセッションで実際に出した不具合は、**そのほぼ全部がこの3種類から出ている**。

- 差分が3桁になった瞬間に本体の数値へ食い込んだ（`191▲153` と繋がって読めない）
- 通知がレポートの結果1行という最重要行に被さった
- 無効表示のディザを文字の上に打ち、ラベルが判読不能になった
- 装備選択のピッカーがスロット矩形と重なり、一覧に到達できなかった
- 看板の板幅より文字が長く、画面外へはみ出した
- パネルの高さを概算で出し、ユニーク効果が枠からあふれて下の行と重なった

**これらはすべて、レイアウトを算術で解いているから起きる。**
`flex` / `grid` に置けば、重なりも溢れも文字幅の測り違いも**構造的に発生しえない**。
テキストの折り返し・省略・禁則はブラウザが持っている。当たり判定はブラウザが持っている。

### 0.3 調査: 生成AIにとって宣言的UIが有利か

外部の知見にも当たった。結論は「**条件付きで有利**」であり、その条件を満たすかを確認した。

**有利とする側の論拠。** LLM は細粒度の手続きが苦手で、GUI 操作の相当部分は決定的に
実行できるため、宣言的なプリミティブに落とすほうが成功率が上がるという報告がある
（[From Imperative to Declarative: LLM-friendly OS Interfaces](https://arxiv.org/html/2510.04607v2)）。
宣言的UIは「どう描くか」ではなく「どうあるべきか」を書くため、保守性・**テスト容易性**・
関心の分離で優れるとされる（[Automated Declarative UI Code Generation](https://arxiv.org/pdf/2409.11667)）。

**不利とする側の論拠も無視しない。** シーン生成の研究では**手続き的なほうが優れる**という
逆の結果が出ている。宣言的DSLは文法が表現力を縛り、さらに
「複雑なDSLは手作りの例で丁寧に説明する必要があり、**説明が長くなるほどLLMは混乱する**」
（[Imperative vs. Declarative for Open-Universe Scene Generation](https://arxiv.org/pdf/2504.05482)）。

**この反証がここに当てはまるかを検討した。当てはまらない。**
反証が問題にしているのは「**その場で定義した独自DSL**」であって、CSS と HTML ではない。
CSS/HTML は学習データ上で最も潤沢な表現体系であり、仕様を長文で与える必要がない。
つまり「DSLの説明が長くなるほど混乱する」というコストは、CSS を使う限り発生しない。
一方で「宣言的なほうがテストしやすい」という利点だけが残る。

なお生成UIの分類では、エージェントが画面をどこまで所有するかで
controlled / declarative / open の3段階が挙げられている
（[Generative UI](https://www.copilotkit.ai/generative-ui)）。本プロジェクトが取るのは
最も統制の効く **controlled**（部品はあらかじめ作り、エージェントは組み合わせるだけ）である。

### 0.4 決定打: 検証できるかどうか

上記より重い理由がひとつある。

**canvas は目視でしか検証できない。DOM は表明で検証できる。**

現行の canvas 実装では、レイアウトが壊れているかを確かめる手段がスクリーンショットを
撮って自分の目で見ることしかなかった。実際このセッションでは、座標をハードコードした
スクリーンショット取得スクリプトが**別の画面を撮り続けていた**事故が起きている
（3枚が完全に同一バイトで、それが致命的なバグの唯一の兆候だった）。

DOM なら、

```js
// 「差分が本体の数値に重なっていない」を、目で見ずに確かめられる
const v = el('.row .v').getBoundingClientRect();
const d = el('.row .d').getBoundingClientRect();
expect(v.right).toBeLessThanOrEqual(d.left);

// 「通知が結果行を覆っていない」も同様
expect(overlaps('.toast', '.headline')).toBe(false);

// 「押せないボタンのラベルが読める」も、要素の色と opacity を直接読める
```

視覚的QAが**自動テストに変わる**。これは生成AIが書くコードベースでは決定的に効く。
批評ループ（`docs/SPEC.md` §11）のC軸のうち、レイアウト起因の項目はテストに落ちる。

### 0.5 結論: 2層に分ける

```
┌─────────────────────────────────────┐
│  L0  World      three.js / WebGL     │ ← 奥行き・光・霧・粒子だけ
│                                      │
│  ┌───────────────────────────────┐  │
│  │  L1〜L3  Interface   DOM/CSS  │  │ ← 文字・数値・操作の全部
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
```

**three.js 側には文字・数値・当たり判定・レイアウトを一切置かない。**
3Dが持つのは「雰囲気」だけで、読ませるものと触らせるものは必ず DOM 側にある。

この分担を守る限り、UIの正しさは DOM の表明で確かめられ、3D の不具合は
「絵が地味／明るすぎる」という**性質の問題**に限定される。両者が混ざると、
「読めないのはレイアウトのせいか、光のせいか」が切り分けられなくなる。

> **禁止**: three.js 側で `TextGeometry` / `CSS2DRenderer` / スプライトへの文字焼き込み /
> raycaster によるUI要素のクリック判定 を使うこと。世界の中のオブジェクトを
> 選ばせたくなった場合も、選択肢は DOM のリストとして出す。

## 1. 情報の層（L1〜L3）

`Balatro型UI設計書` §1 を踏襲する。すべての画面はこの3層のどこかに情報を置く。

| 層 | 定義 | 置き場所 | このゲームでの中身 |
|---|---|---|---|
| **L1 常時** | 頻繁に確認する。常に見える | 上端バー（固定） | 所持金・難易度ティア・潜行中の人数 |
| **L2 判断** | いま決めるために見る | パネル／カード | 装備と比較・撤退ルール・派遣先・戦利品・見どころ |
| **L3 詳細** | 必要な人だけ見る | 展開・シート | ユニーク効果の全文・アフィックス内訳・この回の数字・ログ |

**L1 は全画面で同じ位置・同じ順序**。所持金は常に右端。これを画面ごとに変えない。

## 2. 画面の全指定

内部解像度の概念は廃止する。`100vw × 100vh` で組み、`dvh` と `env(safe-area-inset-*)` を使う。
基準は縦持ち 390×844。横持ちは対象外（`orientation: portrait` を推奨表示）。

### 2.0 全画面共通の骨格

```
┌──────────────────────────┐
│ safe-area top            │
│ ┌──────────────────────┐ │
│ │ TopBar    (L1)       │ │  固定・高さ 56px
│ └──────────────────────┘ │
│                          │
│   （World が透けて見える） │  ← 上部 40〜45%
│                          │
│ ┌──────────────────────┐ │
│ │ Stack     (L2)       │ │  スクロール領域
│ │  Panel / Card / List │ │
│ └──────────────────────┘ │
│ ┌──────────────────────┐ │
│ │ ActionBar (L2)       │ │  固定・主要動線1つ
│ └──────────────────────┘ │
│ safe-area bottom         │
└──────────────────────────┘
```

**親指到達域の規約。** 6.5インチ級では親指の弧が届くのは下部に限られ、主要操作は
下端に寄せるべきとされる（[Mobile game design](https://game-ace.com/blog/mobile-game-design/)、
[Game UI Design Guide 2025](https://generalistprogrammer.com/tutorials/game-ui-design-complete-interface-guide-2025)）。
したがって:

- **主要動線（CTA）は必ず ActionBar（画面下端）に置く。** 上端には置かない
- 上端バーは**表示専用**。唯一の例外は「戻る」1つ（左上・慣習に従う）
- タップ対象の最小寸法は **44×44px**
- 破壊的操作（売却・解体）は確認シートを挟み、**確認ボタンを右**に置く

**World の見せ場を上に置く。** 下半分はパネルが覆うため、3Dの被写体は画面の
上40〜45%に収める。縦画面は水平画角が垂直FOV×アスペクト(≈0.46)まで狭まるので、
カメラは想定より大きく引く（モック作成時、17mまで寄って小屋だけで横幅が埋まった）。

### 2.1 タイトル `TitleScreen`

| 要素 | 層 | 指定 |
|---|---|---|
| World | L0 | `scene: surface` — 夜の地表と、そこから下へ抜ける竪坑。奥に月 |
| ロゴ | — | `DELVERS` серif 大 + 副題「潜る者たち」 |
| CTA | L2 | 「はじめる」1つ。ActionBar |
| seed 表示 | L3 | 左下・極小・`--faint` |

セーブがあれば CTA は「つづきから」。**選択肢を増やさない**（起動直後に迷わせない）。

### 2.2 拠点 `BaseScreen`

このゲームの中心。設計書 §9「ゲームが現在何をしているのか」を答える唯一の場所。

| 要素 | 層 | 指定 |
|---|---|---|
| World | L0 | `scene: lodge` — 夜の小屋。窓に灯り、焚き火、燠火の粒 |
| TopBar | L1 | 所持金 / 難易度 / 潜行中N |
| `DispatchSlot` × N | L2 | 冒険者ごとに1枚。**誰が・どこへ・あと何分**を必ず1行で |
| `ActionGrid` | L2 | 2×2。開封 / レポート / 派遣 / インベントリ。バッジ付き |
| `HireCard` | L2 | 次の派遣枠。条件と費用と「雇う」 |
| `ProgressStrip` | L3 | 踏破 n/10・図鑑 n・難易度 |

**DispatchSlot の状態は3つだけ**（潜行中／待機中／装備不足）。それ以外を作らない。
潜行中は進捗バーと残り時間を出す。待機中は「いつでも出せる」と即座に出発できる導線を出す。

### 2.3 派遣準備 `DispatchScreen`

プレイヤーが行う3つの判断（装備・撤退ルール・派遣先）を1画面に収める。

| 要素 | 層 | 指定 |
|---|---|---|
| World | L0 | `scene: descent` — 選択中ステージの深さまで松明が灯る |
| `EquipRow` | L2 | 武器・防具の2枠。タップで Picker へ |
| `MatchupHint` | L2 | 属性の噛み合いを1行。⚠ か ◎ を先頭に |
| `RuleCards` | L2 | 撤退ルール3枚。**選択前でも3枚の違いが読めること** |
| `StageList` | L2 | 解放済みは属性タグと所要時間。未解放は費用と条件 |
| `StageDetail` | L3 | 敵属性・弱点・耐性・ドロップ傾向・出る敵・ボス名 |
| `EtaLine` + CTA | L2 | 実測の所要時間レンジ。ActionBar に「派遣する」 |

**所要時間は必ず実測のレンジで出す。** ステージ全長を出してはならない
（実時間は到達深度に比例するため、全長表示は常に嘘になる）。
深度0で終わる見込みなら、派遣**前**に警告を出す。

### 2.4 装備選択 `PickerSheet` → `CompareView`

**Loot → Compare → Equip の3段を必ず踏ませる。** 一覧のタップで即装備してはならない。

| 段 | 要素 | 指定 |
|---|---|---|
| Loot | `ItemList` | 候補一覧。装備中との差を ▲▼ で先に見せる |
| Compare | `EquipCard` × 2 | 左=装備中 / 右=候補。数値ごとに差分 |
| | `Verdict` | 「差し引きどちらが強いか」を1行で言い切る |
| Equip | ActionBar | 「戻る」「装備する」 |

比較中も**一覧は下に残す**。別の行を叩けばそのまま比べ直せること。
（毎回「戻る」を挟ませると、複数候補の比較が現実的でなくなる）

### 2.5 帰還レポート `ReportScreen`

| 要素 | 層 | 指定 |
|---|---|---|
| World | L0 | `scene: descent` — 到達深度まで光の帯が伸びる |

### 2.6 開封 `OpeningScreen`

**この作品で唯一、演出に予算を集中する画面**（`docs/SPEC.md` §9.4）。

| レアリティ | World | 演出 |
|---|---|---|
| 並 | 静止 | 一覧に流れて着地するだけ |
| 上質 | 微かな明滅 | 着地時に小さく跳ねる |
| 稀少 | `scene: reveal` 紫 | カットイン。紙片120。溜め1.2秒 |
| 遺物 | `scene: reveal` 金 | 暗転→溜め2.4秒→破裂。紙片160。ユニーク効果を1文字ずつ開示 |

## 3. コンポーネントの全指定

すべて DOM。各コンポーネントは**単独で再利用でき、状態を4つ持つ**。

### 3.1 状態モデル

タッチ専用のため hover は存在しない。設計書 §7 の hover→focus→selected を次に読み替える。

| 状態 | 見た目 | 用途 |
|---|---|---|
| `normal` | 既定 | — |
| `pressed` | 1px沈む・影が消える | 指が触れている間 |
| `selected` | 枠が accent 色・地が持ち上がる | いま選ばれている |
| `disabled` | 不透明度 0.38・影なし | 押せない |

**触れないものにこの4状態を付けてはならない。** 逆に触れるものには必ず全部付ける。

### 3.3 ボタンの段（重要度の階層）

**問題:** 選択肢がすべて同じ見た目で並ぶと、プレイヤーは「次に何をすればいいのか」を
毎回自分で考えることになる。拠点の4枚のタイルは同じ大きさ・同じ色で、
未開封が7個あるときも何も無いときも同じ顔をしていた。

一般的な指針は一致している——**1画面に強調は1つだけ**置き、残りは段を落とす
（[Carbon][c] / [LogRocket][lr] / [Cieden][ci]）。主要動線は下端に置くほど速く届く
（[UX Movement][ux]）。放置ゲームでは、条件を満たした瞬間に主要動線を
小さなアイコンから中央の目立つ表示へ移しただけで、その行動が28%増えた例がある
（[The Mind Studios][ms]）。

[c]: https://v10.carbondesignsystem.com/components/button/usage/
[lr]: https://blog.logrocket.com/ux-design/types-of-buttons-in-ui-design/
[ci]: https://cieden.com/book/atoms/button/how-to-create-button-hierarchy
[ux]: https://uxmovement.com/mobile/optimal-placement-for-mobile-call-to-action-buttons/
[ms]: https://games.themindstudios.com/post/idle-clicker-game-design-and-monetization/

**4段。**

| 段 | 見た目 | 意味 | 1画面あたり |
|---|---|---|---|
| `primary` | 金の塗り＋縁＋影 | **いま押すべきもの** | たかだか1つ |
| `secondary` | 枠線のみ・文字は通常色 | 同じ場面で選べる別の道 | 0〜3 |
| `quiet` | 枠なし・文字は淡色 | 戻る・閉じる・やめる | 制限なし |
| `danger` | 赤の枠線 | 取り消せない操作 | 0〜1 |

**規則。**

1. `primary` は必ず ActionBar（親指到達域）に置く。本文の中に置かない。
2. **取り消せない操作を `primary` にしない。** 誤タップの代償が非対称なので、
   売却・破棄は `danger` 止まりにする。確認モーダルの中だけは `primary` を許す
   （そこでは「押すべきこと」が本当にそれだから）。
3. **「戻る」「閉じる」を `primary` にしない。** 次にやることではない。
   図鑑と所持品は読む・整理する画面なので、`primary` を持たなくてよい。
4. バッジ（赤丸）は「そこに未処理がある」ことだけを言う。
   バッジが付いても段は上がらない。段を決めるのは重要度、バッジが示すのは件数。
5. 無効なボタンは段を1つ落として見せる。ただし文字は読めるまま（§7.1 U6）。

**拠点の動線。** ActionBar の1つが状況で行き先を変える。順序は

> 待機中の冒険者がいる → 未鑑定品がある → 未読レポートがある → 所持品を整理

放置ゲームでは**空いている生産枠が最も高くつく**（開封は待てるが、
待機中の冒険者は時間をただ捨てている）。タイル側は、その行き先を
`secondary` で示して「ActionBar が指しているのはこれ」と分かるようにする。

### 3.4 EquipCard の中身の順序（固定）

設計書 §3 §4 に従い、上から**この順序で固定する**。画面ごとに入れ替えない。

```
1. アイコン
2. レアリティ           ← 色は §4.3 のレアリティ色
3. 名前
4. 主要数値             ← 最重要。武器は秒間火力を先頭に
5. 特殊効果（アフィックス） ← ★でティア
6. ユニーク効果          ← 枠で囲い、全文を折り返して出す
7. 状態（ロック・装備中）
```

**武器は必ず「秒間火力」を先頭に置く。** 威力はベースタイプが違うと比較にならないため、
プレイヤーが強弱を判断できる唯一の数字がこれである。並び替えもこの値で行う
（表示している数字と並び順が食い違ってはならない）。

### 4.7 派遣中に見えるもの（改善指示書 §4）

**出来事は捏造しない。** 派遣した瞬間に本物のシミュレーションが走り切って

印の位置がバーの伸びを追い越していないこと）。

### 4.8 板の作り（改善指示書 §5）

**問題:** 同じ角丸・同じ塗り・同じ幅の板が縦に積まれていて、
「量産ダッシュボード」に見えていた。ドット絵路線には戻さない判断なので、
板そのものの作りと配置で差を出す。画像は使わない——増やすと管理する資産が増え、
品を追加するたびに描き足しになる。

| 手 | 何を崩すか |
|---|---|
| 四隅の切り欠き | 「角丸の矩形」という一様さ |
| 見出しを上の罫に載せる（銘板） | 板の中に見出しがある一様さ |
| 上端だけ明るい斜めの光 | 単一トーンの塗り |
| 数字をセリフ体に | 均一フォント |
| 画面ごとに面の色をごく僅かに寄せる | 全画面が同じ紺 |
| 主役のタイルだけ幅いっぱい | 均等グリッド |

役割色（攻撃の赤・回復の緑・レアリティ）は**動かさない**。
同じ「攻撃」が画面ごとに違う赤になってはいけない（静的検査 §4 が見ている）。

タイルは**3列**にする。2列のままだと、幅いっぱいの1枚を除いた3枚が
2+1 に割れて、最後の1枚が半端に取り残される。どのタイルが主役になっても
割り切れる形を選ぶ。

## 6. three.js 側の規約

### 6.1 やってよいこと

- 奥行き（霧・被写界深度なしの遠近）
- 光（点光源・スポット・発光マテリアル・ブルーム）
- 粒子（燠火・塵・紙片）
- ゆっくりしたカメラの漂い（振幅は画面の5%以内、周期10秒以上）

### 6.2 やってはならないこと

- **文字・数値の描画**（`TextGeometry` / `CSS2DRenderer` / スプライトへの焼き込み）
- **UI要素の当たり判定**（raycaster でボタンを押させない）
- 画面全体を単色で埋めるフラッシュ
- 1秒あたり複数回の画角変化・激しいカメラワーク

### 6.3 資産の規約

- **外部テクスチャ・外部モデルを読み込まない。** 基本形状＋ライティング＋霧＋発光で作る
  （読み込み失敗で画が壊れる経路を持たない）
- 金属表現には環境マップを必ず入れる（`metalness` を上げた面は映り込む対象が無いと真っ黒になる）
- ブルームは閾値を高く取る（`threshold ≥ 0.7`）。低いと画面全体が発光して文字が溶ける

### 6.4 性能予算

| 項目 | 上限 |
|---|---|
| ドローコール | 150 |
| 三角形 | 60,000 |
| 同時ライト | 8 |
| 粒子 | 400 |
| フレーム時間 | 16.7ms（1画面あたり、中位端末で） |

タブが非表示のときは `requestAnimationFrame` を止める（バッテリーを焼かない）。
WebGL が使えない端末では**3Dを諦めて静的な背景に落とす**。UIは DOM なので機能は全部残る。

### 6.5 装備の3Dモデル

`src/world/models.ts`。9ベース × 4レアリティ × 5属性 = 180通りを
**箱と円柱から組む**。アセットで持つと追加のたびに作り直しになるし、
読み込みの失敗という新しい壊れ方が増える。

| 何を伝えるか | 何で伝えるか |
|---|---|
| ベース（何を手にしたか） | 形。刃渡り・刃幅・鍔幅・柄長で6種を描き分ける |
| レアリティ | 素材の質と装飾の数（並0個〜遺物3個）。**形は変えない** |
| 属性 | 刃・結晶の色。物理は素の鋼 |

**規則。**

1. **形はレアリティで変えない。** 変えると「同じ短剣なのに別物」に見え、
   比較の助けにならない。変えてよいのは金属らしさ・光り方・宝珠の数だけ。
2. **大きさは境界箱から決める。** 手で倍率と位置を書くと、モデルを1つ足すたびに
   台座からはみ出したり埋まったりする。実寸と読ませたい背丈（`READ_SIZE`）の
   両方を使って、原点中心・既知の高さに整える。
3. **広い面は暗く。** 剣1本のために組んだ明るさで鎧の胴を照らすと、
   受ける光の量が桁違いで白く飛ぶ。素材側に面積の補正を持つ。
4. **平たいものは回さない。** 弓を台座の上でぐるりと回すと、半周のあいだ
   真横を向いてただの棒になる。左右に振るだけにする。
5. 見せるのは **開封のカットイン** と **所持品の明細** の2箇所だけ。
   どちらも「3Dが画面の上から3割、数字は下」で揃える。

被写体の高さは1シーンにつき1つの定数で決める。光条・光輪・紙片・被写体を
別々の数字で置いていたら、光が集まる点と品の位置がずれていた。

### 6.6 画面ごとのシーン（ビジュアル改善指示書 §3）

**シーンは捨てずに取っておく。** 遷移のたびに作り直していたので、
拠点へ戻るたびに星も焚き火も塵も最初からやり直しになっていた。
「裏で常駐している世界」に見せたいなら、作り直してはいけない。

**3つの層。** 星空（最遠・霧の外）／遠景の山（中景・視差）／前景の主役。
背景の層は**近景用の霧に入れない**——密度 0.055 の FogExp2 は 100m 先で
ほぼ完全な不透明になり、置いた星も山も1つも見えていなかった。

**上から3〜4割はシーンに明け渡す**（`.stack.hero`）。3D を作り込んでも、
UIカードが上から下まで埋めていたら見えない。入ってくる中身は霞ませて、
板が唐突に途切れないようにする。

**画面の状態は `Mood` で渡す。** 画面が three.js に触らずに済むよう、
渡すのは数値だけ（`accent` / `intensity` / `presence`）。
文字は渡さない——World層は光と密度でしか喋らない（§6.1）。

| 画面 | 何を映すか | 状態で何が変わるか |
|---|---|---|
| 拠点 | 星・遠景の山・小屋・煙・焚き火 | 潜行中は灯りが落ち、片方の窓が消える |
| 派遣準備 | 覗き込むダンジョンの入口 | 派遣先の属性で奥の光の色、深さで塵の密度 |
| 装備選択 | 一点を照らす展示台 | レアリティで光の色とオーラの強さ |
| 帰還レポート | 到達深度まで灯る竪坑 | 派遣先の属性で色、追い詰められた回ほど松明が揺れる |
| 開封 | 光の奔流（既存・他画面の基準） | レアリティで強度4段 |

色の切り替えは瞬間ではなく 0.2〜0.3 秒で寄せる。パッと変わると
「設定が切り替わった」に見えて、場所が変わった感じがしない。

**点光源を増やさない**（§3 パフォーマンス方針）。窓ごとに置いていた光は
家全体を照らす1灯にまとめ、窓ごとの表情はスプライトで作る。

## 7. 検証の規約

**この節が本文書の目的である。** UIの正しさは目視ではなく表明で確かめる。

### 7.1 必ず書くテスト

| # | 内容 | 表明 |
|---|---|---|
| U1 | 要素が重なっていない | 同一パネル内の兄弟の矩形が交差しない |
| U2 | 文字が枠から溢れていない | `scrollWidth <= clientWidth` |
| U3 | タップ対象が44px以上 | 全 `button` の矩形が 44×44 以上 |

| U6 | 無効ボタンのラベルが読める | 計算後の色のコントラスト比 ≥ 3:1 |

| U8 | 通知が文字を覆わない | Toast と**文字を持つ要素すべて**が交差しない |
| U9 | 200件で操作が1フレーム以内 | 並び替え・絞り込みの所要が 16.7ms 未満 |
| U10 | reduced-motion が効く | 指定時に `--d-*` が 0 |
| U11 | 押せると見えるものが押せる | 中心を叩くとその要素が返る（暗幕の層を考慮） |
| U12 | 浮かせた文字が他を踏まない | `position:absolute` の文字と本文が交差しない |
| U13 | primary は1画面に1つ、ActionBar の中 | `[data-tier=primary]` が1個以下 |
| U14 | 取り消せない操作が primary でない | 売却・破棄のラベルが primary でない |
| U15 | 段が宣言されている | `[data-tier]` が1つ以上ある |
| U16 | World層が白飛びしていない | 飽和画素が全体の3%以下 |
| T5/T6 | 開封の数値が上がり、閃光が消える | 時間を置いて2回測る |
| T7/T8 | サムネが全行に出て、組み合わせ単位で焼かれている | 焼いた枚数 ≤ 所持品の組み合わせ数 |
| T9 | 派遣中に先の出来事が見えない | 印の位置 ≤ バーの伸び |

U8 は当初「結果行と交差しない」だった。拠点には結果行が無いので判定が素通りし、
実際には通知が「インベントリ」に被っていた。**表明そのものが素通りしうる**ので、
「その表明が効いているか」を変異試験（わざと壊して落ちることの確認）で見る。

U16 は `?probe=1` のときだけ描画結果を読めるようにして測る（常時だと毎フレームの複製が増える）。

### 7.2 目視でしか確かめられないもの

3Dの**構図と雰囲気**だけ。明るさは U16 で測る（「眩しすぎる」は言葉にしづらいが、
飽和した画素の割合なら測れる）。ここはスクリーンショットで確認する。
**その際、座標を決め打ちしたスクリプトを信用しない**——このセッションでは
決め打ち座標のせいで3枚が同一バイトになり、それが致命的なバグの唯一の兆候だった。
スクリーンショット取得は必ず `data-screen` 属性を読んで、撮れている画面を確認してから撮る。

| §4 | TypeScript に色の直書きが無いか | 同じ「攻撃」が画面ごとに違う赤になる |
| §6.1 | World層に文字を描く手段が無いか | 3D側に文字が漏れ、測れない表示ができる |
| §3 | 画面が DOM を直接いじっていないか | 同じ状態から同じ画面になる保証が消える |

### 8.4 移行で見つかった破綻

DOM へ移したこと自体が、canvas では見つけようがなかった不具合を出した。
以下はすべて**表明で検出した**もので、スクリーンショットでは分からない。

| 破綻 | 検出 |
|---|---|
| タップが再描画に重なると黙って消える | U11 を書く過程 → 専用の再現試験 |
| 通知が戦利品の行に被っていた | U8 |
| シート表示中に TopBar の戻るが押せない | Playwright の到達可能性判定 |
| 開封の CTA が親指到達域の外に出ていた | U4 |
| `.row` がパネル内で効かず、ラベルと値が地の文になる | 図鑑の目視 → U1 の対象拡大 |
| U8 自身が拠点で素通りしていた | U8 の対象を「文字を持つ要素すべて」に広げて発覚 |
